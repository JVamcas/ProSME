## Findings and acceptance

### Funding Opportunities client slice

- Applicant screens 2 and 3 are implemented at
  `/portal/funding-opportunities` and its stable ID-based detail route.
- Interactive server state follows component → TanStack Query hook → client
  service → applicant API route → server service → Payload integration.
- The integration projects only published `funding-calls`; Payload remains the
  content owner and no application-domain copy is persisted.
- List search and status filtering run in Payload, and the list uses bounded
  cursor pagination with a stable unique ordering. A reusable pagination
  control provides page ranges and previous/next navigation for every status
  tab. Responsive cards, detail information, loading, empty, retryable-error,
  malformed-slug,
  unauthenticated, and disabled-user behavior are covered.
- The existing public eligibility guidance is linked for open calls. Versioned
  portal assessments and application-start actions remain pending until their
  later P3.2 slices are implemented.
- The detail view follows the approved screen hierarchy with Overview,
  Eligibility, Key information, Documents, and Contact tabs; its overview
  combines an about panel with readiness and deadline cards.
- Opportunity and application states use the shared brand-compliant
  `StatusBadge` primitive with statically discoverable Tailwind classes.
- The funding browser composes the shared `Tabs`, `FormInput`, `EmptyState`,
  `Pagination`, loading, and error-state primitives rather than duplicating
  those controls within the feature. Search is registered through React Hook
  Form and validated by the funding-opportunity Zod search schema.
