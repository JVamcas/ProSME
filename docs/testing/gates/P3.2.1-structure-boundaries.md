## Scope

- Make applicant, admin, public, shared-layout, and shared-UI component
  ownership explicit in source paths.
- Use flattened `Client<Domain>Service.ts` and `Server<Domain>Service.ts`
  naming so execution boundaries are visible without opening a file.
- Keep application lifecycle states inside the application domain rather than
  creating state-specific files or service families.
- Separate business behavior, schemas, types, and client state from the
  applicant-profile domain.
- Move the existing protected admin application endpoint from the ambiguous
  `/api/applications` path to `/api/admin/applications`.
- Change structure and naming only; do not implement P3.2 product behavior.

## Findings and acceptance

### Implemented structure

- Application browser requests live in `ClientApplicationService.ts`; server
  policy and orchestration live in `ServerApplicationService.ts`.
- The same explicit client/server convention is used for businesses, profiles,
  and engagement. Content server entry points and Firebase client/server entry
  points also identify their execution boundary.
- Applicant, admin, and public feature components are grouped first by their
  owner and then by domain. Shared layout and UI remain in their shared paths.
- Business schemas, types, hooks, client transport, and server orchestration
  now belong to the businesses module rather than the profiles module.
- The existing protected operations application route is now
  `/api/admin/applications`; no ambiguous `/api/applications` route remains.
- Lifecycle state remains application data. No status-named service,
  repository, component family, or API boundary was introduced.
