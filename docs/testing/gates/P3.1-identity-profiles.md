## Implemented scope

| Area | Implementation |
| --- | --- |
| Shared shell | One `AuthenticatedPortalShell` composes applicant and operations route spaces; SME Fund logo; desktop orange sidebar; branded mobile header; breadcrumbs, search, help and capability-gated notifications |
| Context | Flat server-created `PortalContext` includes status, named role/capability arrays, available spaces and default space; the Firebase subject remains server-only |
| Query discipline | Named user columns, roles, capabilities and both dashboard completion flags are projected by one SQL query; layouts and nested pages share a React request cache |
| Route filtering | Separate applicant/operations catalogues use recursive capability filtering and remove inaccessible empty parents |
| External navigation | `Available Funding` declares new-tab behavior in the route catalogue; the shared renderer adds `_blank`, `noopener noreferrer`, and assistive text |
| Capability gate | Reusable single, any, all, resource-scope, hide, fallback and forbidden modes; server-side policies remain authoritative |
| Space routing | Dual-scope users receive an applicant/operations switcher; default sign-in routing is derived from active capabilities |
| Administrator bootstrap | Bootstrap assigns both `system_administrator` and `applicant` additively, so the account retains operations authority while receiving its own applicant profile workspace |
| Applicant profile | Owned PostgreSQL record including applicant position, explicit SQL projection, protected `GET/PATCH` API, independently validated and persisted personal/contact RHF/Zod forms, and recoverable UI states |
| Profile tabs | Reusable accessible tab primitive; Personal information, Contact details and Change password remain addressable under `/portal/profile`, filtered by read capability, with view-only controls when update capability is absent |
| My Businesses | Owned PostgreSQL collection, shared DataTable, protected list/detail CRUD APIs, and RHF/Zod add/edit forms under `/portal/businesses` |
| API envelopes | Context and profile APIs return `{data, meta}` success or structured `{error, meta}` failure envelopes with correlation IDs; unexpected profile failures are logged with the same correlation ID |
| Ownership | APIs derive the owner from the verified session; no request payload accepts a user or owner identifier |
| Audit | Profile upsert and immutable audit insert execute atomically; audit metadata records changed field names without duplicating personal values |
| Migration | `0006` creates profile/audit tables; `0007` enables independent applicant profile sections; `0008_applicant_businesses.sql` removes the one-business-per-user constraint and adds the ownership index |
| Operations applications | Navigation, page and backend service require `application.read.assigned` or `application.read.all`; assigned-only reads use a repository scope that returns no placeholder records until assignments exist |
| Dashboard | Compact approved welcome/status/recent-activity hierarchy with truthful zero and unavailable states until later increments provide projections |
| Desktop top bar | Approved search-first composition with persistent notification state and an initials/avatar user menu; the borderless menu joins the header edge and dismisses on outside click or Escape |
| Shell states | Shared branded loading and error presentations are generic and caller-configurable for both `/portal` and `/admin`; route adapters separately own default workspace copy and Next.js error/reset behavior |

## Responsive and accessibility evidence

- The desktop navigation is hidden below the `lg` breakpoint; a sticky mobile
  header and menu replace it.
- Both navigation renderings use a labelled `nav`; the active route uses
  `aria-current="page"`; the mobile control has an accessible name.
- Decorative icons are hidden from assistive technology. Standalone icons use
  primary orange, with navy used on the orange sidebar surface for contrast
  and orange restored for the active navy item.
- Every profile control is rendered through labelled shared form components.
  Validation errors use `aria-describedby` and `aria-invalid`; pending and
  error states expose `status` or `alert` semantics.
- `portal-shell.test.tsx` renders the real shell and verifies navigation
  labelling, current-route state, the mobile control, SME Fund identity and
  capability-gated content.
- `applicant-dashboard.test.tsx` and `profile-workspace.test.tsx` verify the
  assigned P3.1 screen hierarchy, truthful empty states, capability-filtered
  profile navigation, view-only behavior, identity summary and canonical
  brand-token usage.

Full cross-browser, assistive-technology and viewport UAT remains part of P3.9;
this record covers the automated component evidence required to review P3.1.
